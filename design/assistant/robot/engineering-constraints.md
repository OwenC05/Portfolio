## Camera, scale and movement

`S/components/studio/scene/view-config.ts` fixes the eye at `[-0.7, 2.8, 3.4]` world units, with **2 units per metre**. Heading zero faces -Z; positive yaw looks +X and positive pitch looks up. Production desktop/mobile vertical FOV is 58°/64°; home yaw/pitch is `[-4,-6]` / `[-13,-8]`; bounds are yaw `[-38,58]`, pitch `[-16,12]`, near/far `0.1/30`. No camera translation, orbit approach or fit-to-robot is supported. Current M3 harness captures instead use 74° on phones; that is not the production `STUDIO_VIEW` value.

`controller.ts` selects mobile rendering at window width <=640 or host aspect <0.9; DPR caps are 2 desktop / 1.5 small. The home pose is chosen once; resize preserves orientation. Inspect the robot at actual desktop, 390 and 320 widths, both camera configurations where applicable, all look bounds, Projects-open and scrollbar modes. Meter size, anchor and swept motion volume remain **pending Claude's proposal and projection/occlusion measurement**. Do not reserve space by moving accepted room objects or changing the camera.

The current renderer has no ambient animation loop; `reducedMotion` is in the public contract but the controller currently needs no animation branch. Robot motion would require explicit live preference handling and bounded invalidation/RAF ownership. Propose a static neutral pose first, with finite event-driven motions only after measured approval; stop on idle, hidden, offscreen and disposal, and suppress nonessential motion for reduced motion. Static shadow maps currently refresh explicitly, not every frame: a moving caster requires shadow invalidation and fresh cost measurements. A noncasting initial proposal avoids that extra refresh requirement, subject to Claude's visual review. No extra lights or postprocessing are proposed.

## Asset handoff and Meshy constraints

The existing room profile is `S/design/studio-v2/asset-pipeline/full-kit/full-kit-profile-v1.json`, implemented by `technical/profile-core.mjs`. It requires known inventory/material/node identities and excludes animations, skins and morphs. **It is not a generic robot loader.** Use a separately versioned robot profile/owner after design approval; do not silently widen the room schema or insert robot nodes into its certified root.

- Deliver an editable `.blend`, paired self-contained GLB, reproducible export settings and manifest: source/export hashes, units, axes, local bounds, named parts/parents, neutral transforms, materials/textures, unique and placed triangles, primitive submissions, shadow flags, raw/compressed bytes and any clip metadata. Count exported triangles, not Meshy's face target.
- Author in metres, Blender Z-up; export Y-up. Existing room conversion is Blender `[X,Y,Z] -> glTF [X,Z,-Y]`, then world scale 2 and +0.11Y once. For a **local-origin robot**, propose a neutral hover-root pivot and a separate world-placement wrapper applying scale 2 once at the approved world anchor; do not also bake the room offset into that local asset. If authored in room coordinates, use the room mapping instead. Record the choice and verify it with bounds/axis markers.
- Separate only approved moving parts. Put each origin at its intended hinge/swivel; preserve parent-child transforms and named pivots. Bake mesh scale/shear corrections without destroying those pivots; avoid negative/reflected transforms. Meshy output may require manual separation, topology repair, retopology, UV cleanup and retexturing. A fused generated mesh is not automatically articulated.
- Prefer ordinary opaque PBR materials and embedded PNG/JPEG where textures are needed; remove hidden/interior geometry and duplicate materials. Do not export Blender lights/cameras, external image paths, unsupported extensions or compression decoders. Transparency, skins, morphs or additional texture slots require explicit profile and cost review; current room image limits are not a robot texture allocation.
- If motion is approved, object-transform animation is the initial engineering candidate for rigid floating parts. Record clip names/durations, rest pose, pivot axes, swept bounds and event bindings; bake constraints to supported transforms. Do not promise humanoid auto-rigging. Do not place meaningful source text solely on a tiny 3D display; keep readable HTML equivalents.

Tool facts are **coordinator-verified inputs from the brief**, not newly tested here: hosted Higgsfield 3D Jutsu imports curated catalog models, not arbitrary user/Meshy GLBs; Blender and 3D Blocking Studio connectors reported disconnected on 15 November; Meshy's multi-image input supports 1-4 views of one object, while its automatic rigging targets humanoid/biped characters. Thus hosted concept/blockout and local Meshy-to-Blender cleanup are separate stages. No session was launched or taken over, local Blender availability was not checked, and no paid job/settings were submitted. Generation settings/credits and connector readiness need checking at the later production handoff.

## Reusable assistant API and truthful visual events

In A, `app/api/assistant/route.ts` constructs `createAssistantHandler` from `lib/assistant/handler.ts` and the published allowlist in `lib/knowledge/catalog.ts`. Reuse same-origin `POST /api/assistant`, JSON `{question: string}`: trimmed length 1-600 JS string units, body <=4096 bytes. Success is `application/x-ndjson`, one event per line, `no-store`; request failures are JSON `{error}` with HTTP status. It is not SSE, a token stream or a reasoning trace.

| `lib/assistant/types.ts` event | Robot/visualization may represent |
| --- | --- |
| `retrieval-start {question}` | Search received/started. Local `requesting` precedes this and must not claim retrieval already occurred. |
| `retrieval {hits, durationMs}` | Actual selected passages and measured search duration. Hit fields: `sourceId, chunkId, title, heading, text, href, score`; score is lexical matching, not confidence. |
| `generation` | Only an actual provider call. It is absent with generation disabled; never animate a fabricated thinking/generation stage. |
| `answer {answer}` | Actual `mode: sources / abstained / generated`, text, citations, optional fallback reason/model. Keep excerpts, source links and contact suggestion visible; matching passages do not establish the question's premise. |
| `done {durationMs}` | Actual request-processing completion/duration, not animation completion. |

`lib/assistant/events.ts::parseAssistantEvent()` validates payload shapes; `components/assistant/AssistantWorkbench.tsx` owns the current request, cancellation, stale-run guard, stream buffering, state and retrieval map. It has **no exported event subscription**, only a `generationEnabled` prop. Later integration may extract/publish its existing run state to a Studio adapter while preserving behavior; do not add another request/parser or improve retrieval in this task. Preserve cancel, timeout, malformed/truncated stream and superseded/unmount handling. Event ordering/semantic support are not proven by shape validation. Fast search may finish before a render; show the resulting real state/history without artificial stage delays. `lib/assistant/generation.ts` and deployment configuration stay disabled; no model changes are part of robot integration.
